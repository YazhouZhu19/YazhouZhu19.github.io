# GitHub projects and Google News discovery

The **GitHub code dashboard** and **Public updates dashboard** sit beside the **Paper dashboard**. Each source dashboard contains a statistical overview and its full searchable library. Their independent snapshot is `data/research-signals.json`; neither source is inserted into the paper archive or counted as a paper in the macro dashboard. Browse by text, broad research area, relevance and dates; owners and publishers appear on each card and remain searchable by text, with no separate owner/publisher dropdown; compare up to three repositories by license, push/release dates, archived state and stars. Stars are a snapshot of attention, not research quality. Code licensing does not establish permissions for model weights, data or clinical use.

## Collection and provenance

`npm run collect:signals` collects public GitHub REST metadata, short README excerpts and the latest stable release, plus Google News public search RSS results. Discovery uses versioned, bilingual catalogues in `lib/github-discovery.ts` and `lib/news-discovery.ts`: modalities, anatomy, clinical tasks, modelling methods, data, evaluation and infrastructure each supply independent retrieval routes. Topic searches and title/description matches supplement selective README searches. Historical repositories remain discoverable, and selected routes include forks. Exact GitHub links already present in the saved paper archive and existing signal metadata supplement keyword discovery; links establish a reference relationship, not authorship or quality.

GitHub searches retrieve up to 100 records per page. Dense queries split into creation-date ranges to reduce the 1,000-result search ceiling. A persistent queue saves pagination and date partitions when the request budget ends, while fair rotation prevents a broad route from starving other directions. Search timeouts, unsplittable dense ranges and pending work remain explicit coverage limitations. The collector never claims an exhaustive census: GitHub indexing, absent metadata, ambiguous acronyms, changed search ordering and API limits still cause omissions.

Google News uses explicit date windows across the bilingual catalogue. Recent windows refresh regularly; historical monthly windows continue from a saved queue, and dense windows split into shorter intervals. Publication dates are checked locally because a search engine can ignore date operators. Saturated one-day windows and failed requests remain queued. This is Google's public RSS discovery interface, not a visitor's browser history or a guaranteed developer API. Google does not promise exhaustive coverage or a stable pagination contract.

Google results retain the named publisher, publication date, discovery URL and Google result link. Search titles and snippets are explicitly labelled `search-snippet`: they are not verified original article text. `originalUrl` remains null unless a public original URL is actually available; Google is not presented as the publisher. The initial collector does not claim to have verified publisher articles or their model-performance claims. Browsing offers an external Google News search for further discovery; those results are not automatically added to the snapshot.

The existing GitHub workflow invokes both collectors. Signal endpoints that last completed successfully with the same query/catalogue version are cached for six hours; `--force` refreshes them immediately. `--news-days N` changes the Google news discovery window (default 365 days). `--github-only` and `--news-only` refresh one source while retaining the other source’s records and check times. `--deep` increases the bounded collection budget for a one-time backfill; repeated runs resume unfinished work. The existing scheduled workflow uses the smaller incremental budget. `--force` bypasses the six-hour cache without erasing the queue. `--input PATH --output PATH` support reviewable collection into a separate file; `--init` explicitly permits a missing initial input. `GH_TOKEN` or `GITHUB_TOKEN`, when present, is sent only to `api.github.com`. There is no browser-side token or shared AI secret.

Requests, response sizes and result counts are bounded. Existing records survive source failures and refreshes. Each endpoint records its real check time, last successful check, received/retained counts and errors. A cached source keeps its original check time. All-source failure records fresh errors and returns a failure status; malformed/oversize input or unexpected fatal failure cannot replace the archive with empty data. CI checks freshness and retained IDs, then verifies that the published signal bytes match the source snapshot. The browser validates the schema and 64 MiB size ceiling, retains its last valid snapshot on failure and loads signals independently of papers.

GitHub search responses supply repository metadata without an extra request for every candidate. README/release enrichment is bounded and rotates across collection cycles; missing enrichment remains unknown. Authentication permits a larger request budget, while the unauthenticated path respects a smaller budget and slower search pacing. Rate-limit failures use bounded handling and preserve the archive. Compact JSON and a 50,000-record / 64 MiB safety bound accommodate a larger library. Reaching either bound fails visibly and preserves the prior snapshot; records are never silently trimmed to fit. Further growth will require sharded storage.

Both source libraries expose a discovery-direction filter with actual collected counts, links to the configured queries, and each record’s matched groups. Counts can overlap across groups. Selecting a group also limits the candidates passed to its AI panel. This filter does not add a fixed taxonomy to the independent Research outlook AI workflow.


## Relevance and candidate review

Transparent rules assign `direct` (explicit medical-imaging context) or `candidate` (ambiguous domain, resource lists, educational examples or indirect links), retaining short reason codes. These are retrieval checks, not AI scoring, human review, scientific quality assessments or verification of functionality. Unrelated finance and sensor-ranging content is excluded. Imaging-related administrative, commercial, personnel, commentary and educational stories remain candidate context rather than direct technical progress. Both libraries default to direct matches; users can include candidate leads and inspect the reasons. Candidate records are excluded from research/PI AI evidence. Legacy unclassified records remain schema-compatible and browsable as candidates, and are excluded from AI evidence until refreshed and classified as direct matches.

## AI and evidence limits

Each source page can analyze its filtered records, with optional paper evidence. **Research outlook** and the independent-question window allow papers, GitHub and news to be selected together, with their own dates and forecast horizon. These use the existing local, free-cloud and paid AI choices; no separate model download is needed beyond the selected model's normal first use. Cloud analysis sends only the selected public evidence and the entered question to the explicitly chosen provider. The provider/model is displayed in the result.

AI inputs carry an explicit evidence kind. Papers describe reported research, repositories describe implementation availability and a current maintenance snapshot, and news describes publisher claims or unverified search snippets. A paper, repository and announcement can describe one work and do not establish independent corroboration. Sampling balances evidence kinds and time buckets; counts and categories cannot establish field-wide prevalence or growth. Results separate observations, conditional forecasts, alternative explanations and proposed validation, with links to exact supplied evidence.

PI/team analysis includes external records only when the selected papers and those records share an explicit URL, DOI or arXiv identifier. The interface exposes this linkage. Neither a link nor a repository owner proves authorship, team membership, PI ownership or private research intent. A lack of matched signals is reported as missing evidence.

GitHub date filters use the latest push, release or creation date; news filters use the reported publication date. Mutable repository metadata and search snippets are eligible for AI only when their observation date is on or before the selected end day. The collector currently keeps the latest observation per record, not a historical time series: it cannot reconstruct past repository state, popularity growth or a past announcement's exact contents. Dates are not backfilled to fabricate retrospective predictions.

Automated tests cover schema/size rejection, malformed responses, bounded discovery, cache/error retention, cross-source sampling and historical cutoffs, exact PI linkage, typed AI payloads, citation rejection and zero-price cloud safeguards. A mocked cloud test verifies the request/response integration; it does not validate a real model's scientific interpretation.

## Browse categories

The source library groups its detailed discovery routes into 13 GitHub research areas and 10 news areas (`lib/signal-browse-categories.ts`). These are browsing aids based on retrieval tags, not independently verified task classifications. Records can belong to multiple areas, so category counts overlap. General-only, unknown and untagged records receive a general category; a generic discovery route does not add that category when a specific area is known. Every record remains reachable. The original query catalog, collector breadth, provenance and snapshot data are preserved; detailed discovery routes remain available under collection scope.

## Source dashboard measurements

`lib/signal-dashboard.ts` calculates deterministic statistics from the same text, area, relevance and date-filtered records displayed by the source library. Each unique record ID contributes at most once to a metric or category; research areas may overlap. The current snapshot's `generatedAt` anchors rolling windows so the results are reproducible. Repository and news records remain separate populations. Charts and headline totals open the exact counted records, with a return to the overview; changing the base filters clears the previous drill subset.

The GitHub overview shows the scoped project count, repositories pushed within the last 90 calendar days, identified code-license metadata, and collected Release metadata. It compares broad research areas, declared main languages and mutually exclusive maintenance states. The twelve-month chart counts each repository at its latest recorded activity date; it is a distribution of current metadata, not commit frequency, popularity growth, historical repository states or field growth. Archived projects take precedence in maintenance states, and missing/invalid/future push dates remain unknown.

The news overview shows scoped announcement count, distinct named publishers, publication within the last 30 calendar days and available original-article URLs. It compares broad areas, publisher composition and the collector's model/research/tooling labels. Publication dates form a twelve-month distribution; a source article is not a unique model release or an independent scientific result. Named publishers are normalized for case/whitespace, not inferred as organizations.

Calendar windows and chart bins use UTC dates to match the source-library date fields. The current month is incomplete. Missing, future and older dates are reported separately from the twelve-month series; static counts still include those records. Top-language and publisher breakdowns retain Other/Unknown buckets so they reconcile with the filtered total. Unknown dates, missing enrichment and unavailable original links are never treated as evidence that a repository lacks releases or a publisher lacks an original article.
