# GitHub projects and public news discovery

The **Open-source insights** and **Frontier updates** sit beside the **Paper insights**. Each source dashboard contains a statistical overview and its full searchable library. Their independent snapshot is `data/research-signals.json`; neither source is inserted into the paper archive or counted as a paper in the macro dashboard. Browse by text, broad research area, relevance and dates; owners and publishers appear on each card and remain searchable by text, with no separate owner/publisher dropdown; compare up to three repositories by license, push/release dates, archived state, stars and forks. Stars are a snapshot of attention, not research quality. Code licensing does not establish permissions for model weights, data or clinical use.

Open-source insights shows total stars and forks, per-repository medians, and separate top-10 rankings for the same deduplicated, filtered repository population as the other charts. Counts come from GitHub's `stargazers_count` and `forks_count` as of each repository's latest `observedAt`; the displayed observation-date range does not imply that every repository was refreshed at the site's generation time. Repository creation/activity filters select the population, not a star/fork growth interval. Summed stars do not represent unique users. Equal counts share competition ranks (1, 1, 3), with repository name and ID breaking display-order ties; an all-equal scope shows the shared value instead of an arbitrary leaderboard. A row opens its project card; total cards and “Full ranking” open the same filtered library sorted by the selected metric. Zero counts remain valid, while empty scopes show no-data states.

## Collection and provenance

`npm run collect:signals` collects public GitHub REST metadata, short README excerpts and the latest stable release, plus Google News public search RSS results and independent publisher RSS/Atom feeds. Discovery uses versioned, bilingual catalogues in `lib/github-discovery.ts` and `lib/news-discovery.ts`: modalities, anatomy, clinical tasks, modelling methods, data, evaluation and infrastructure each supply independent retrieval routes. Topic searches and title/description matches supplement selective README searches. Historical repositories remain discoverable, and selected routes include forks. Exact GitHub links already present in the saved paper archive and existing signal metadata supplement keyword discovery; links establish a reference relationship, not authorship or quality.

GitHub searches retrieve up to 100 records per page. Dense queries split into creation-date ranges to reduce the 1,000-result search ceiling. A persistent queue saves pagination and date partitions when the request budget ends, while fair rotation prevents a broad route from starving other directions. Search timeouts, unsplittable dense ranges and pending work remain explicit coverage limitations. The collector never claims an exhaustive census: GitHub indexing, absent metadata, ambiguous acronyms, changed search ordering and API limits still cause omissions.

Google News uses explicit date windows across the bilingual catalogue. Recent windows rotate by their actual check time, with separate recent-check checkpoints; two recent requests and one historical request share each bounded budget when both queues have work. Cached recent results do not block unfinished history. Historical monthly windows continue from a saved queue, and dense windows split into shorter intervals. Publication dates are checked locally because a search engine can ignore date operators. Saturated one-day windows and failed requests remain queued. This is Google's public RSS discovery interface, not a visitor's browser history or a guaranteed developer API. Google does not promise exhaustive coverage or a stable pagination contract.

Google results retain the named publisher, publication date, discovery URL and Google result link. Search titles and snippets are explicitly labelled `search-snippet`: they are not verified original article text. `originalUrl` remains null unless a public original URL is actually available; Google is not presented as the publisher. The initial collector does not claim to have verified publisher articles or their model-performance claims. Browsing offers an external Google News search for further discovery; those results are not automatically added to the snapshot.

Independent feeds are configured in `lib/news-sources.ts` and fetched directly, without passing through Google. Only exact configured feed URLs are fetched, with redirects disabled and no GitHub credentials. RSS/Atom dates, public article hosts and record metadata are validated; the collector stores short publisher excerpts and original links, not full articles. Feed retention limits available history. Publisher excerpts are labelled separately from search snippets and do not establish independent validation. New feed IDs use canonical article URLs. Cross-channel matching uses canonical URLs or matching publisher/title within one day, with explicit publisher aliases; conflicting original URLs remain separate. Merges preserve existing IDs and first-seen timestamps and never replace a publisher excerpt with a search snippet. Existing historical IDs are not deleted.

The Google catalogue now combines 24 thematic routes with 24 publisher-targeted routes, including research institutions, professional imaging media, model developers, imaging vendors, and Chinese research publishers. Not-yet-attempted routes use `pending` with no check timestamp; only real requests count as successes or failures. The source list is bounded at 160 entries.

The existing GitHub workflow invokes all collectors. Signal endpoints that last completed successfully with the same query/catalogue version are cached for six hours; `--force` refreshes them immediately. `--news-days N` changes the news eligibility and Google discovery window (default 365 days). `--github-only` and `--news-only` refresh one source while retaining the other source’s records and check times. `--deep` increases the bounded collection budget for a one-time backfill; repeated runs resume unfinished work. The existing scheduled workflow uses the smaller incremental budget. `--force` bypasses the six-hour cache without erasing the queue. `--input PATH --output PATH` support reviewable collection into a separate file; `--init` explicitly permits a missing initial input. `GH_TOKEN` or `GITHUB_TOKEN`, when present, is sent only to `api.github.com`. There is no browser-side token or shared AI secret.

Requests, response sizes and result counts are bounded. Existing records survive source failures and refreshes. Each endpoint records its real check time, last successful check, received/retained counts and errors. A cached source keeps its original check time. All-source failure records fresh errors and returns a failure status; malformed/oversize input or unexpected fatal failure cannot replace the archive with empty data. CI checks freshness and retained IDs, then verifies that the published signal bytes match the source snapshot. The browser validates the schema and 64 MiB size ceiling, retains its last valid snapshot on failure and loads signals independently of papers.

GitHub search responses supply repository metadata without an extra request for every candidate. README/release enrichment is bounded and rotates across collection cycles; missing enrichment remains unknown. Authentication permits a larger request budget, while the unauthenticated path respects a smaller budget and slower search pacing. Rate-limit failures use bounded handling and preserve the archive. Compact JSON and a 100,000-record / 64 MiB safety bound accommodate a larger library. The record bound allows valid snapshots past the former 50,000-record ceiling; the byte limit remains unchanged. Reaching either bound fails visibly and preserves the prior snapshot; records are never silently trimmed to fit. Further growth will require sharded storage.

Both source libraries expose a discovery-direction filter with actual collected counts, links to the configured queries, and each record’s matched groups. Counts can overlap across groups. Selecting a group also limits the candidates passed to its AI panel. This filter does not add a fixed taxonomy to the independent Research outlook AI workflow.


## Relevance and candidate review

Transparent rules assign `direct` (explicit medical-imaging context) or `candidate` (ambiguous domain, resource lists, educational examples or indirect links), retaining short reason codes. These are retrieval checks, not AI scoring, human review, scientific quality assessments or verification of functionality. Unrelated finance and sensor-ranging content is excluded. Imaging-related administrative, commercial, personnel, commentary and educational stories remain candidate context rather than direct technical progress. Both libraries default to direct matches; users can include candidate leads and inspect the reasons. Candidate records are excluded from research/PI AI evidence. Legacy unclassified records remain schema-compatible and browsable as candidates, and are excluded from AI evidence until refreshed and classified as direct matches.

## AI and evidence limits

Each source page can analyze its filtered records, with optional paper evidence. **Research outlook** and the independent-question window allow papers, GitHub and news to be selected together, with their own dates and forecast horizon. These use the existing local, free-cloud and paid AI choices; no separate model download is needed beyond the selected model's normal first use. Cloud analysis sends only the selected public evidence and the entered question to the explicitly chosen provider. The provider/model is displayed in the result.

AI inputs carry an explicit evidence kind. Papers describe reported research, repositories describe implementation availability and a current maintenance snapshot, and news describes publisher claims or unverified search snippets. A paper, repository and announcement can describe one work and do not establish independent corroboration. Sampling balances evidence kinds and time buckets; counts and categories cannot establish field-wide prevalence or growth. Results separate observations, conditional forecasts, alternative explanations and proposed validation, with links to exact supplied evidence.

PI/team analysis includes external records only when the selected papers and those records share an explicit URL, DOI or arXiv identifier. The interface exposes this linkage. Neither a link nor a repository owner proves authorship, team membership, PI ownership or private research intent. A lack of matched signals is reported as missing evidence.

GitHub AI evidence windows use the latest push, release or creation date; news evidence windows use the reported publication date. The repository browser independently supports either latest activity or initial creation dates. Mutable repository metadata and search snippets are eligible for AI only when their observation date is on or before the selected end day. The collector currently keeps the latest observation per record, not a historical time series: it cannot reconstruct past repository state, popularity growth or a past announcement's exact contents. Dates are not backfilled to fabricate retrospective predictions.

Automated tests cover schema/size rejection, malformed responses, bounded discovery, cache/error retention, cross-source sampling and historical cutoffs, exact PI linkage, typed AI payloads, citation rejection and zero-price cloud safeguards. A mocked cloud test verifies the request/response integration; it does not validate a real model's scientific interpretation.

## Browse categories

The source library groups its detailed discovery routes into 13 GitHub research areas and 10 news areas (`lib/signal-browse-categories.ts`). These are browsing aids based on retrieval tags, not independently verified task classifications. Records can belong to multiple areas, so category counts overlap. General-only, unknown and untagged records receive a general category; a generic discovery route does not add that category when a specific area is known. Every record remains reachable. The original query catalog, collector breadth, provenance and snapshot data are preserved; detailed discovery routes remain available under collection scope.

## Source dashboard measurements

`lib/signal-dashboard.ts` calculates deterministic statistics from the same text, area, relevance and date-filtered records displayed by the source library. Each unique record ID contributes at most once to a metric or category; research areas may overlap. The current snapshot's `generatedAt` anchors rolling windows so the results are reproducible. Repository and news records remain separate populations. Charts and headline totals open the exact counted records, with a return to the overview; changing the base filters clears the previous drill subset.

The GitHub overview follows the paper dashboard's structure. `lib/github-dashboard.ts` adds global library size, today's additions and an independently inspectable earliest collection batch. The collector preserves `firstSeenAt` when refreshing a repository. The earliest exact timestamp in the full library is an inferred baseline, not an explicit or complete initial-import marker; its identity does not change with area or relevance filters, and both repository-date statistics include these records when their dates match the selected range. Backfilled old repositories count as library additions, not new repository releases.

GitHub readers can choose 7, 30, 90 days, all dates or a custom interval, using latest repository activity (the default) or initial repository publication. Latest activity uses the latest valid push, Release or creation timestamp. Initial publication uses only `publishedAt`, collected from GitHub `created_at`; it does not assert when a private repository became public or when its first Release appeared, and never falls back to collection or Release time. Both date series can precede the monitor's collection history; dates after a stale snapshot are unknown, not zero. The current Beijing day determines "today", while the snapshot limits available evidence. Lines separate all records, directly relevant records and review candidates using their current relevance labels. Activity dates describe current metadata, not historical commits or repository-state changes. Long ranges are grouped by month. Shared dropdowns match the paper dashboard. Charts, recent projects and library date sorting share the selected date basis and population; global totals and date-exclusion buckets open their exact IDs separately.

GitHub headline cards retain scoped project count, repositories pushed within the last 90 calendar days, identified code-license metadata, and collected Release metadata. Direction, maintenance, language and recent-record views remain available. GitHub calendar boundaries use Beijing time, including 90-day push groups. Archived projects take precedence in maintenance states, and missing/invalid/future push dates remain unknown. The overview defaults to all leads for composition; AI assessments still exclude review candidates.

The news overview follows the same dashboard layout and shared dropdowns as the paper/GitHub views. `lib/news-dashboard.ts` provides a global library count, today's first collections and an inspectable inferred earliest batch. The four scoped cards show message count, distinct named publishers, model-related records and tool/platform records. A source article is not a unique model release or an independent scientific result. Type labels follow collection rules; publisher names are normalized for whitespace/case, not inferred as independent organizations. Original-link coverage remains a data note, not a claim of verification.

News readers can select 7/30/90 days, all dates or a custom interval, by source publication time (default) or platform first collection. The overview starts with all relevance levels; candidates remain in the library but do not enter AI assessments. Calendar windows, cards and chart bins use Beijing dates. Publication counts include the earliest collection batch whenever publication dates match; discovery counts separate that fixed batch and do not draw observations before collection began. The news evidence cutoff is the latest valid successful news-source observation or retained news-record observation, bounded by the overall snapshot timestamp. Failed checks and GitHub-only refreshes cannot advance this cutoff; successful empty news searches can. Dates after this cutoff remain unknown rather than zero, and invalid/future dates are separately inspectable. Long windows aggregate by month, with partial edge months disclosed. Charts, recent messages, filters and library sorting share the same date basis and exact record IDs. Source check times are shown separately from the shared snapshot generation time.

The type ring and publisher buckets reconcile to the scoped population; broad research areas can overlap. Top-language and publisher breakdowns retain Other/Unknown buckets. Unknown dates, missing enrichment and unavailable original links are never treated as evidence that a repository lacks releases or a publisher lacks an original article.

## Repository maturity — 2026-10-21-v1

Maturity is separate from the unchanged `direct`/`candidate` relevance rules.
`established` means at least 50 stars, at least 10 forks, or a DOI/arXiv link in
`relatedUrls` plus at least 10 stars. `active` requires a push within the preceding
180 days and an identified license, a README excerpt with at least 200 normalized
characters, or at least 5 stars. Other repositories are `early`; archived
established repositories are capped at `active`. Placeholder licenses, impossible
or future push dates, and whitespace-only README text do not qualify. The snapshot
instant anchors this rule, so repeated views of the same data are reproducible.

The overview defaults to established plus active repositories and offers an
“Include early repositories” checkbox. Global library/addition totals still count
all records; the resource library searches all maturity levels. Chart drills and
full rankings retain the exact overview population. Maturity never deletes or
changes a record, and neither stars nor these levels establish scientific quality,
reproducibility, maintenance guarantees or clinical effectiveness.

A 200-record stratified audit of the existing direct population is exported in
`eval/github-direct-review.csv`, with frozen evidence, Codex provisional labels and
empty human-review columns. The labels describe public metadata, not a tested
implementation. No direct-relevance rule is tightened before human confirmation.
